# ADR-0002. Размещение базы данных в приватной подсети

**Статус**: принято

**Дата**: 2026-10-18

## Контекст

Проект TimeCapsule (PHP, nginx, PHP-FPM, PostgreSQL) ранее работал на одном экземпляре EC2, где приложение и база данных использовали общие ресурсы сервера. В ЛР3 инфраструктура разделена на `app-server` в публичной подсети и `db-server` в приватной подсети VPC `timecapsule-dev-vpc`. Необходимо выбрать размещение PostgreSQL, которое обеспечит доступ приложению, ограничит возможность внешних подключений и позволит независимо обслуживать базу данных.

## Решение

PostgreSQL размещается на отдельном экземпляре `db-server` в приватной подсети `timecapsule-dev-private-a` без публичного IP-адреса. Приложение подключается к базе по DNS-имени `db.timecapsule.internal` через приватную зону Route 53. Security Group `timecapsule-dev-db-sg` разрешает подключения на порт 5432 только от `timecapsule-dev-web-sg`, а `pg_hba.conf` дополнительно ограничивает доступ пользователем и базой `timecapsule`. Административный SSH-доступ осуществляется через bastion.

## Рассмотренные альтернативы

1. **База данных на одном сервере с приложением, как в ЛР2.** Отклонено: простая настройка и отсутствие сетевого соединения между серверами, но приложение и PostgreSQL конкурируют за CPU и RAM. Сбой или удаление единственного экземпляра одновременно затронет приложение и базу данных, а независимое обслуживание и масштабирование невозможно.
2. **База данных на отдельном сервере в публичной подсети.** Отклонено: ресурсы приложения и PostgreSQL разделены, а обновления можно устанавливать через Internet Gateway без NAT Gateway. Однако публичная подсеть допускает маршрут в интернет, и при назначении публичного IP и ошибке настройки Security Group база может оказаться доступной извне.
3. **База данных на отдельном сервере в приватной подсети.** Выбрано: PostgreSQL изолирован от прямых входящих подключений из интернета, а приложение обращается к нему по внутренней сети VPC. Это усложняет настройку и обслуживание, но снижает риск несанкционированного доступа и позволяет независимо управлять сервером базы данных.

## Последствия

**Становится лучше**: база данных изолирована от интернета, доступ ограничен Security Group и pg_hba.conf. Приложение и PostgreSQL работают независимо, а приватная зона Route 53 позволяет обращаться к базе по DNS-имени вместо IP-адреса.

**Становится хуже**: инфраструктура усложняется и требует дополнительных расходов на EC2. Для обновления db-server необходимо временно создавать NAT Gateway, стоимость которого составляет около $0.045 в час и $0.045 за ГБ трафика, плюс $0.005 в час за публичный IPv4. После обновлений шлюз и Elastic IP удаляются для сокращения расходов.

**Остающиеся риски**: db-server остаётся единственной точкой отказа, поскольку резервирование базы данных отсутствует. При его сбое приложение потеряет доступ к данным, поэтому необходимы регулярные резервные копии.

Elastic IP обеспечивает постоянный публичный адрес app-server после перезапусков. При появлении Application Load Balancer пользователи будут обращаться через балансировщик, поэтому отдельный Elastic IP серверу больше не потребуется.

**Точка роста**: переход на Amazon RDS Multi-AZ, добавление балансировщика нагрузки и резервных экземпляров приложения в разных зонах доступности, перенос пользовательских файлов в Amazon S3.
