# ADR-0001. Способ доставки кода на сервер: деплой скриптом deploy.sh

**Статус**: принято

**Дата**: 2026-10-05

## Контекст

Проект TimeCapsule (PHP, nginx, PHP-FPM, PostgreSQL) работает на одном экземпляре EC2, код лежит в публичном репозитории GitHub, секреты вынесены в `.env` на сервере и в репозиторий не попадают. Нужен способ доставлять новые версии кода на сервер репетативно. После обновления кода обязательно выполнить `composer install`, применить изменения базы и перезагрузить PHP-FPM, иначе сайт падает или работает на неполноценной версии.

## Решение

Деплой выполняется скриптом `deploy.sh`, который хранится в репозитории и запускается на сервере одной командой. Скрипт начинается с set -euo pipefail, чтобы прерываться при первой ошибке, и выполняет фиксированную последовательность: `git pull --ff-only`, `composer install --no-dev --optimize-autoloader --no-interaction`, `php bin/init-db.php`, `sudo systemctl reload php-fpm`, с echo-метками между шагами для понятного лога и выводом хеша последнего коммита в конце.

## Рассмотренные альтернативы

1. Копирование файлов через `scp`. Отклонено: нет привязки к версии, на сервере непонятно какой коммит развернут, при каждом деплое нужно вручную перечислять файлы и легко забыть один или залить лишний, репозиторий и сервер со временем рассинхронизируются, а `composer install` и перезагрузку FPM все равно нужно выполнять отдельно.
2. `git pull` вручную на сервере с ручным выполнением остальных команд. Отклонено: версия на сервере соответствует коммиту, но состав и порядок шагов держится в голове исполнителя, легко пропустить composer `install` или `reload` и приложение упадёт, после неудачной команды можно по инерции продолжить следующие и усугубить поломку, а процедура не задокументирована в исполняемом виде.

## Последствия

Становится лучше: деплой воспроизводим одной командой, ошибки прерывают процесс вместо продолжения в сломанном состоянии, лог деплоя читаем по меткам шагов, новый человек понимает процедуру чтением скрипта, изменения процедуры попадают в историю через коммиты.

Становится хуже: процедуру нужно поддерживать в актуальном состоянии, изменение шагов деплоя требует правки скрипта и коммита, деплой по-прежнему ручной и требует SSH-доступа к серверу.

Остающиеся риски: деплой не атомарен, в окне между `git pull` и `reload php-fpm` сайт может отвечать ошибками, автоматического отката и smoke-тестов после деплоя нет, а `/health` не покрывает поломки шаблонов и vendor, поэтому неудачный деплой может быть не замечен мониторингом и обнаружится только глазами, как в упражнении с поломкой. Откат выполняется вручную через `git revert` и повторный деплой.

Точка роста: при росте проекта `deploy.sh` станет шагом пайплайна CI/CD, после деплоя добавятся smoke-тесты ключевых страниц, а переключение версий станет атомарным через симлинк на релизную папку.
