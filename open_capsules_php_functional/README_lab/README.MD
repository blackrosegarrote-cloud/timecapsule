### Задание 3. Мониторинг и диагностика

![alt](images/status_check_instance.png)

Раздел Status and alarms, в нем есть также подразделы:

- System status check проверяет инфраструктуру AWS: физический сервер и сеть, на которых работает экземпляр
- Instance status check проверяет саму виртуальную машину: загрузилась ли операционная система и отвечает ли она
- Attached EBS status check проверяет, доступны ли подключённые тома EBS

На скриншоте можно увидеть, что с этим экземпляром нет никаких проблем на данный момент.

**Вопрос**

- **Какая из проверок укажет на проблему, которую можете исправить вы, а какая на проблему на стороне AWS?**
  - Instance status check - проблема пользователя. Вероятные проблемы в этом разделе: проблемы с загрузкой ОС, хранилище переполнено, сбиты настройки сети - всё это находится в зоне ответственности пользователя и настраивается им самим, так что устранение этих проблем его забота и исправляется им же.
  - System status check - проблема на стороне AWS. Сюда входят: неисправность физического хоста, гипервизора и прочие проблемы, которые решает сам AWS, поскольку это касается их оборудования.
  - Attached EBS status check - формально, причина на стороне AWS, но рискует потерять данные пользователь. Поскольку диск относится к оборудованию AWS, пользователь не несет за него отвественность и исправляет неполадки именно AWS, но он не гарантирует сохранность данных в процессе починки диска, потому что проблемный диск может отказать в любой момент, поэтому следует сделать снимок тома, чтобы затем из него восстановить данные. Исходя из этого, проблему решает как сам пользователь, так и AWS.

![alt](images/monitoring.png)

Раздел Monitoring состоит из:

- CPU utilization (%) — процент времени, в течение которого процессоры экземпляра были заняты вычислениями, значение около 0.2% означает практически полностью простаивающую машину.
- Network in (bytes) — объём данных в байтах, полученный экземпляром из сети за период измерения, редкие пики соответствуют входящим обращениям, например SSH-подключениям или HTTP-запросам.
- Network out (bytes) — объём данных в байтах, отправленный экземпляром в сеть за период, пики на графике - это ответы сервера внешним клиентам.
- Network packets in (count) — количество входящих сетевых пакетов за период, то есть интенсивность входящего трафика в штуках, а не в объёме.
- Network packets out (count) — количество исходящих сетевых пакетов за период, парная метрика к предыдущей для исходящего направления.
- Metadata no token (count) — число обращений к Instance Metadata Service без токена безопасности, то есть по устаревшему IMDSv1; ноль на графике означает, что метаданные запрашиваются только по безопасному IMDSv2 или не запрашиваются вовсе.
- CPU credit usage (count) — количество CPU-кредитов, потраченных за период на работу выше базового уровня производительности.
- CPU credit balance (count) — накопленный запас кредитов, доступных для всплесков нагрузки выше базового уровня, ровная линия около 289 говорит, что машина почти не выходит за базовую производительность и запас не тратится.

**Вопрос**

- В каких случаях стоит включать детальный мониторинг?
  - Детальный мониторинг следует влючать в период коротких и резких всплесков нагрузок, поскольку 5-минутная метрика - средний показатель за 5 минут и всплеск нагрузки длительностью в минуту просто растворится. Его следует включать так же и в периоды отладки, а еще в production-сервисах, где минута простоя из-за какой-то невыявленной вовремя ошибки будет стоить дороже, чем плата за детальную метрику.

![alt](images/stop_instance.png)

Остановка экземпляра с помощью CloudShell

**Вопросы**

- **Чем Stop отличается от Terminate?**
  - Stop только выключает экземпляр, все данные сохраняются. Операционная система останавливается, корневой и дополнительные EBS-тома остаются со всеми данными, и экземпляр можно запустить снова.  
  Terminate удаляет экземпляр безвозвратно: корневой том по умолчанию удаляется вместе с данными, запустить такой экземпляр снова нельзя.
- **За что вы продолжаете платить, пока экземпляр остановлен?**
  - После остановки экзмепляра пользователь по прежнему платит за хранилище. Дополнительно в стоимость могут входить, например, сохраненные снапшоты и Elastic IP, если таковые имеются.

**Вопросы**

- **git pull заменяет файлы по одному, и это занимает несколько секунд. Что может увидеть посетитель, который откроет сайт в этот момент?**
  - Сайт может показать ошибку или сломаться. `git pull` обновляет файлы последовательно, и в какой-то момент код оказывается в промежуточном состоянии, когда одни файлы уже новые, а другие ещё старые, и приложение падает с фатальной ошибкой, выдавая посетителю 500 Internal Server Error или белый экран.
- **Что случится с сайтом, если после git pull не выполнится composer install?**
  - Если в новом коммите обновились зависимости в `composer.json`, то в `vendor/` их не будет и приложение упадёт с ошибкой "class not found" при попытке использовать новый код, зависящий от отсутствующих библиотек.
  Если зависимости не менялись, то ничего не сломается, но это везение, а не правило, поэтому composer install в скрипте деплоя обязателен для гарантии согласованности кода и зависимостей.

**Вопросы**

- **Почему /health отвечает ok, хотя главная страница не работает?**
  - Потому что это отдельный обработчик, который проверяет только проверяет доступность БД и наличие таблиц, делая SELECT-запрос к таблице `users`. Он не проверяет остальные слои на наличие ошибок, следовательно для него отсутствие проблем с БД достаточно, чтобы ответить ok.
- **Что на самом деле проверяет этот адрес?**
  - Он проверяет доступность БД и наличие таблиц, выполняя реальный запрос `SELECT COUNT(*) FROM users`, а не пинг соединения, поэтому 500 от него означает либо недоступную БД, либо отсутствие таблиц.
- **Чего не хватает такой проверке?**
  - Ей не хватает проверки остальных слоёв: vendor, шаблонов, роутинга главной и статики, поэтому при сломанной главной health продолжает отвечать ok и даёт ложное спокойствие.

### Контрольные вопросы

**1. Как проходит запрос от браузера до базы данных в вашем развёртывании? Какую роль играет каждая программа?**

Браузер отправляет HTTP-запрос на публичный IP экземпляра. Его встечает Security group и решает пускать ли соединение. Затем nginx принимает соединение, отдаёт статику из public/ и передаёт динамические запросы дальше PHP-FPM, где свободный рабочий процесс выполняет PHP-код приложения, который по ходу выполнения обращается к PostgreSQL через драйвер. PostgreSQL читает и пишет данные в своих файлаз на EBS-томе и возвращает результат, после которого PHP отдаёт готовый HTML или JSON  обратно в браузер через nginx.

**2. Почему сервер может скачивать код из репозитория, но не может отправлять в него изменения? Почему для сервера это правильно?**

Репозиторий публичный, так что clone и pull доступны без аутентификации, а push требует учетные данные (SSH-ключ, как в этом приложении) с правом записи. Это правильно по принципу минимальных привилегий и благодаря этому подходу, если злоумышленник получит доступ к серверу, он не сможет запушить вредоносный код на удаленный репозиторий.

**3. Что произойдёт с загруженными пользователями файлами, если удалить экземпляр EC2? Как это связано с тем, что вы знаете об EBS?**

При удалении экзмепляра по умолчанию EBS-том тоже удаяется, следовательно загруженные пользователем файлы исчезнут. EBS-том переживает перезагрузки и остановки, но его жизненный цикл привязан к экземпляру (флаг delete on termination), из чего следует, что данные пользователя существуют, пока сущетсвует экземпляр и будут потеряны, если не сделать предварительно снапшоты.

**4. Что общего у вашего deploy.sh или последовательности команд варианта A с тем, что делают системы CI/CD? Чего в вашем процессе ещё не хватает?**

Общее то, что `deploy.sh` - это по сути пайплайн деплоя: доставка кода, получение кода, установка зависимостей, миграция БД, перезапуск сервис, но CI/CD-выполняет это автоматически. Не хватает автоматического триггера вместо ручного запуска, тестов, автоматического отката при падении тестов и атомарного переключения версий, чтобы не было простоя между `git pull` и `reload php-fpm`.
