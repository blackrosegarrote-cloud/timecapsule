# ADR-0003. Хранение вложений пользователей в Amazon S3

**Статус**: принято

**Дата**: 2026-10-19

## Контекст

В проекте TimeCapsule (PHP, nginx, PHP-FPM, PostgreSQL) вложения капсул ранее сохранялись в `storage/uploads` на диске `app-server`. Такой способ привязывает пользовательские файлы к одному экземпляру EC2: при замене сервера или запуске второго экземпляра вложения придётся переносить и синхронизировать. Необходимо выбрать хранилище, доступное независимо от жизненного цикла сервера приложения, с ограниченным доступом и защитой от случайного удаления.

## Решение

Вложения хранятся в бакете Amazon S3 `timecapsule-dev-uploads-blackrosegarrote` под префиксом `uploads/`. Приложение обращается к S3 с временными учётными данными роли EC2 `timecapsule-dev-app-role` и политикой `timecapsule-dev-app-s3`, предоставляющей только `s3:GetObject`, `s3:PutObject` и `s3:DeleteObject` для объектов `uploads/*`. Список объектов приложению недоступен. Бакет блокирует публичный доступ, требует HTTPS и использует шифрование SSE-S3.

При загрузке вложение получает случайное имя объекта. При открытии капсулы приложение после проверки прав пользователя создаёт подписанный URL сроком на пять минут и перенаправляет браузер на S3. В бакете включено версионирование и правило `timecapsule-dev-noncurrent` для старых версий объектов под `uploads/`.

## Рассмотренные альтернативы

1. **Диск EBS сервера приложения.** Отклонено: простое и привычное файловое хранение, но вложения зависят от конкретного тома и экземпляра. Для нескольких серверов нужны перенос данных, общее подключение либо синхронизация, а восстановление зависит от резервных копий.
2. **Общая файловая система Amazon EFS.** Отклонено: несколько экземпляров EC2 могут одновременно использовать общую файловую систему с привычными файловыми операциями. Однако необходимы настройка сетевого доступа, монтирование и отдельный контроль стоимости хранения и обращений к файлам.
3. **Бакет Amazon S3.** Выбрано: объектное хранилище не зависит от отдельного EC2, предоставляет API для загрузки и удаления, поддерживает версионирование, Lifecycle и временные подписанные ссылки. Потребовалось изменить модуль хранения приложения, поскольку S3 не является обычной файловой системой.

## Последствия

**Становится лучше**: вложения больше не зависят от диска `app-server`. Пользователь получает файл напрямую из S3 по подписанному URL после проверки прав в приложении. Подпись привязана к конкретному запросу и ограничена сроком пять минут; для временных учётных данных срок ссылки также ограничен временем действия этих данных. Публичный доступ к бакету остаётся закрытым.

**Становится хуже**: приложение зависит от доступности S3 и сети, а работа с файлами требует AWS SDK. Хранение, запросы и передача данных могут создавать дополнительные расходы. Подписанную ссылку можно передать другому человеку, и до истечения её срока он сможет получить тот же файл.

**Остающиеся риски**: версионирование защищает от случайного обычного удаления: вместо уничтожения данных создаётся `Delete marker`. Приложению не разрешено окончательно удалять версии через `s3:DeleteObjectVersion`. Правило Lifecycle переводит подходящие неактуальные версии в Standard-IA через 30 дней, удаляет старые версии после 90 дней с сохранением двух последних неактуальных версий и очищает незавершённые multipart-загрузки через 7 дней. Сохранённые версии продолжают занимать место, а две защищённые неактуальные версии могут храниться бессрочно.

**Точка роста**: при запуске нескольких экземпляров приложения за Application Load Balancer все серверы смогут обращаться к одному бакету S3 с одинаковой IAM-политикой, без копирования вложений между дисками. Для полноценного масштабирования также потребуется общее хранилище сессий, согласованная конфигурация приложения и доступ всех экземпляров к одной базе данных.
